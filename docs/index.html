Hand-crafting an NES ROM in F#

This is the Chrome dinosaur game, rebuilt for the NES. An F# script writes the ROM byte by byte: 6502 instructions and larger snippets are F# functions that append bytes to an array, and running the script saves that array as dino.nes. The build has no assembler and no linker.

Named snippets over byte arrays

A snippet is an F# function that appends bytes. Its name says what the bytes do, and its doc comment says which registers it changes. The game is mostly calls to snippets: jump (), fall (), checkHits (). Inside each one, every byte is still chosen by hand. The examples below come from the real build. The script was run with a tracer that recorded which line put each byte.

Checks while the ROM is built

The build is a normal F# program, so it can print, compute and assert as it writes bytes. Snippets check their own arguments, and the game script checks its tuning. A failed check stops the build with a message, before any ROM is written.

The library also fails the build on its own: a branch that can't reach its label, a zero-page operand above $FF, an addressing mode the instruction doesn't have, or a file that doesn't match its iNES header.

Checks on the result

The bytes aren't checked by reading them. They're checked by running them. Each snippet is a short, fixed byte sequence with known inputs and outputs, so it could also be checked formally: a superoptimizer can search every shorter sequence for one that does the same thing. This project doesn't do that yet.

In an emulator

After each build, FCEUX runs the ROM headless with a Lua script. The script plays the game and compares it to a model written in Lua: jump heights, air time, jetpack fuel, stomps, and the score on screen.

In a debugger

The build writes FCEUX symbol files next to the ROM, so the debugger shows fall and dino_vy instead of bare addresses.

Across refactors

A cleanup of the F# should leave the ROM unchanged, so the check is that its SHA-1 stays the same. sizeOf measures what a snippet costs in bytes before you pick between inlining it and making it a subroutine.

What replaces the assembler and linker

An assembler provides labels, macros and expressions, and a linker places the result in memory. Here each of those is ordinary F#.

Usual buildgame.asm→assembler→game.o→linker + config→game.nes
This buildDino.fsx→dotnet fsi Dino.fsx→dino.nes+ symbol files
FeatureIn this build
InstructionsA function per mnemonic. LDA (Imm 0x40) appends A9 40. An addressing mode the 6502 doesn't have for that instruction fails the build.
LabelsF# values: let loop = here "loop", then BNE loop. Labels compare by identity, so two with the same name don't clash.
MacrosFunctions. whenPressed 1 Button.A (fun () -> …) takes the guarded code as an argument.
Expressions, constantsF# evaluated at build time: jumpSpeed = -5.5 becomes the 8.8 fixed-point bytes $80 $FA.
GraphicsTiles are drawn as lists of strings, and a short function converts them to CHR bit planes.
Layoutorg sets the address. A jump to a label not placed yet gets a placeholder, and finishRom fills it in at the end. A subroutine's body is put once, and only if something calls it.
The emulator on this page is jsnes. Any language that can append to a byte array could do the same. F# works well for it because snippets are just functions, labels are values, and build-time code runs in the same script.
